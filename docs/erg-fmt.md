# `erg fmt` の使い方

Erg のコードフォーマッタ。設計と実装の経緯は [erg-fmt-design.md](erg-fmt-design.md) を参照。

```console
$ erg fmt src/            # src/ 以下の .er を全部その場で整形
$ erg fmt --check .       # 書き換えず、変わるファイル名だけ出す（CI 用）
$ erg fmt --stdout a.er   # 結果を標準出力へ
```

## 何をするか

| 対象 | 動作 |
| ---- | ---- |
| インデント | ネスト1段あたり空白 `--indent` 個（既定 4） |
| 連続する空行 | `--max-blank-lines` 行に丸める（既定 2） |
| ファイル先頭・末尾の空行 | 削除 |
| ファイル末尾 | 改行1個で終端 |
| 行末の空白 | 削除 |
| 二項演算子 | 前後に空白1個（`x+1` → `x + 1`） |
| `,` `;` `:` | 前を詰め、後ろに空白1個（`f(a,b)` → `f(a, b)`） |
| `(` `[` の内側 | 詰める（`f( 1 )` → `f(1)`） |
| `=` `->` `=>` `<:` `:>` | 前後に空白1個 |
| 括弧内の継続行 | 括弧の入れ子の深さでインデント |
| `\` で続く行 | 1段インデント。`\` はそのまま残る |
| `--max-width` 超過行 | 括弧の内側のカンマで折り返す |
| 改行コード | 入力が CRLF なら CRLF のまま |

## 何をしないか

**行を結合しない。** 折り返しは「割る」方向にのみ働く。既に複数行に分かれている式を
1行に戻すことはしない。展開したまま残したい呼び出しは、そう書いておけばそのまま残る。

**括弧の外では改行しない。** `a + b + c + ...` のような長い式は、括弧がなければ
長いまま出力される。

**式を書き換えない。** 括弧の付け外し、`if` の並べ替えなどはしない。

**型検査を要求しない。** パースが通らないコードでも lex できれば整形する。
lex もできなければ、そのファイルには一切触らない。

### 流儀が割れているものは原文のまま

次の3つは、どちらの書き方も広く使われているので**触らない**:

```erg
x**2        # そのまま        x ** 2      # これもそのまま
f x:=1      # そのまま        f(x := 1)   # これもそのまま
{ .x = 1 }  # そのまま        {"a": 1}    # これもそのまま
```

`{ }` は record を `{ .x = Int }`、dict を `{"a": 1}` と書き分ける習慣があり、
トークン列からはどちらか判別できない。`( )` `[ ]` は全用途で詰めるので詰める。

### 空白が意味を変える箇所も原文のまま

Erg では並置が適用なので、**空白の有無そのものが意味**を持つことがある:

```erg
f(1, 2)                  # 引数2個
f (1, 2)                 # タプル1個
discard .Name.parse(x)   # discard の呼び出し
discard.Name.parse(x)    # discard の属性アクセス
1.0f64                   # Float 変換
T|Int|                   # 型適用
```

これらはすべて**同じトークン列**になる。どちらのつもりで書いたかはソースにしか
現れないので、被演算子どうしの隣接では原文の空白をそのまま残す
（空白の連続だけは1個に潰す）。

### 行末コメントの位置も原文のまま

```erg
a = 2.5f64           # Float
b: Float = 1.0f64    # 注釈つき
```

列を揃えた行末コメントは揃ったまま残る。整列パスがない以上、
一度潰したら復元できないため。

## 整形させたくないとき

```erg
# fmt: off
matrix = [1, 0, 0,
          0, 1, 0,
          0, 0, 1]
# fmt: on

x = compute(a,b)  # fmt: skip
```

| 書き方 | 効果 |
| ------ | ---- |
| `# fmt: off` | この行以降を整形しない |
| `# fmt: on` | 再開する（`off` のまま終わればファイル末尾まで） |
| `# fmt: skip` | その行（括弧で複数行に分かれていればその論理行全体）を整形しない |

綴りは**厳密**に一致する必要がある。`#fmt:off` や `# FMT: OFF` はただのコメント。
「効いているつもりで効いていない」ほうが「明らかに何もしない」より悪いため。
末尾の空白だけは無視する（エディタでは見えないので）。

ファイル単位で外すなら `--exclude`:

```console
$ erg fmt --exclude vendor --exclude .d.er .
```

パスの**部分文字列**一致（glob ではない）。複数回指定できる。

## フラグ

| フラグ | 既定値 | 意味 |
| ------ | ------ | ---- |
| `--indent <n>` | `4` | ネスト1段あたりの空白数 |
| `--max-blank-lines <n>` | `2` | 連続してよい空行の上限 |
| `--max-width <n>` | `100` | 行長の上限 |
| `--check` | | 書き換えず、変わるファイル名を出す。差分があれば終了コード1 |
| `--stdout` | | ファイルに書き戻さず標準出力へ |
| `--exclude <substr>` | | このパス文字列を含むファイルを飛ばす（複数可） |

設定ファイルはない。理由は [設計書 §12](erg-fmt-design.md)。

オプションはファイルパスより**前**に置くこと（`erg` 共通の制約）:

```console
$ erg fmt --check src/     # OK
$ erg fmt src/ --check     # NG
```

`erg fmt` は `erg --mode fmt` と書いても同じ。
パイプ入力と `-c` は書き戻す先がないので常に標準出力へ出る:

```console
$ cat a.er | erg fmt
$ erg fmt -c 'x  =  [1,2]'
x = [1, 2]
```

## CI で使う

```yaml
- run: erg fmt --check .
```

差分があれば終了コード1で落ちる。

**lex できなかったファイルは落とさない。** stderr に

```text
broken.er: left unformatted: the source could not be tokenized
```

と出るが終了コードには影響しない。`erg fmt` を実行しても直らない類の問題であり、
`erg check` のほうがずっと具体的に指摘できるため。

## エディタで使う

ELS が `textDocument/formatting` に対応している。VS Code なら

```json
{ "editor.formatOnSave": true }
```

で保存時に走る。エディタの `tab_size` が `--indent` として使われる
（`insert_spaces: false`（タブインデント）は無視される。Erg のレキサはタブを
受け付けないため）。

型検査を経ないので大きなワークスペースでも即座に返る。書きかけで構文エラーが
ある状態では**何もしない**（編集を返さない）ので、保存のたびにエラーが出ることはない。

切りたい場合は `els --disable formatting`。

## 壊れないことをどう保証しているか

Erg は空白が意味論的に有意な言語で、`x + 1` は加算、`x +1` は `x` を `+1` に適用する
呼び出しになる。空白規則が少しでも間違っていれば、フォーマッタが黙ってプログラムの
意味を変えうる。

そこで **`erg fmt` は整形結果を必ず lex し直し、元とトークン列が一致するか検証する**。
一致しなければ整形結果を捨てて原文を返す。

つまり **`erg fmt` のバグは「整形されない」で済み、「コードが壊れる」にはならない。**

この検証で捕まらないのは「トークン列が同じなのに意味が違う」場合だけで、
それが上の「空白が意味を変える箇所も原文のまま」の理由である。

## トラブルシューティング

**整形されないファイルがある**

stderr を見る。`the source could not be tokenized` なら lex できていない
（`erg check <file>` で原因が分かる）。
`formatting would change the program` が出たらフォーマッタのバグなので、
そのファイルを添えて報告してほしい。

**長い行が折り返されない**

括弧の内側にカンマがないと割れない。`--max-width` を超えても、
割る場所がなければそのまま出す。

**折り返してほしくない呼び出しがある**

trailing comma を置いておけば展開されたまま残る:

```erg
_ = f(
    1,
    2,
)
```

`erg fmt` は既存の改行を結合しないので、これは幅に収まっても展開されたままになる。
（trailing comma の追加も削除もしない。トークンが1つ増減するとそもそも検証を通らない。）
